# 運用ルール索引と実行ゲート

## 1. 目的

本書は、Q-Scout for Spring の横断運用規程を ChatGPT が作業開始時に参照しやすくするための入口文書である。

運用ルール文書が増えると、個別規程は存在していても、実作業時に必要な規程の参照漏れ、完了条件の誤認、Codex投入指示書の必須項目漏れが発生しやすくなる。

そのため、本書では既存規程を弱めず、以下を一元化する。

- 最優先原則
- 実行主体分類
- 作業開始ゲート
- Codex投入ゲート
- ChatExec / ChatExec2切替ゲート
- PR / CI / mergeゲート
- 完了状態定義
- 詳細規程への参照導線

本書は詳細規程を置き換えない。判断に迷う場合は、本書を入口として詳細規程を確認し、より厳格な規程を優先する。

---

## 2. 最優先原則

以下は全作業に優先する。

1. 要求仕様、ユーザー指定文言、実装方針、テスト期待値、運用規則を弱めない。
2. 安全チェックやツール制約を通す目的で、仕様を曖昧化、マイルド化、部分削除しない。
3. 一部反映、未コミット、未push、PR未作成、CI未確認、main未反映を完了扱いしない。
4. 実装済み・未実装・一部反映・未反映・未確認を明確に区分して報告する。
5. Codex、ChatExec方式、ユーザー手作業へ切り替える場合も、要求仕様を維持する。
6. Q-Scout for Spring はSpringプロジェクトの診断・改善支援系として扱い、対象外の設計生成系仕様と混同しない。
7. `main` への直接push、秘密情報の出力・コミットを行わない。

---

## 3. 実行主体分類

| 実行主体 | 担当範囲 | 主な判断基準 |
|---|---|---|
| ユーザー(人) | 最終判断、外部サービス操作、merge判断、主観評価、手動検証 | AIが代替できない判断または外部権限が必要な場合 |
| ChatGPT(会話内) | 整理、レビュー、比較、計画、Codex指示書作成、作業分解 | 会話内で完結し、リポジトリ状態を直接変更しない場合 |
| ChatGPT(リポジトリ編集) | 小〜中規模文書修正、README更新、docs整理、軽微な設定変更、PR確認 | 対象ファイルを完全取得でき、差分が局所的で安全な場合 |
| Codex | 実装、複数ファイル修正、テスト更新、ビルド確認、PR作成 | コード変更、テスト実行、複数ファイル整合が必要な場合 |

大きい台帳、長大README、長文設計書、既存内容を完全取得できないファイル、Controller / Service / テンプレート / テストを横断する作業は Codex 優先とする。

---

## 4. 作業開始ゲート

作業開始時、ChatGPTは次を確認する。

1. Memory上のプロジェクト運用ルール。
2. `PROJECT_START_PROMPT.md` または本リポジトリの開始時指示。
3. 本書 `00_運用ルール索引と実行ゲート.md`。
4. 対象タスクに関係する詳細規程。
5. Open PRの有無。
6. 直前タスクのmerge、課題管理整理、リモート作業ブランチ削除、ローカルprune前提。
7. 作業主体分類。
8. 未実装機能を実装済みとして扱わないこと。

作業開始時点でOpen PRや直前タスクの未整理がある場合は、新規正規TSKへ進む前に状態を明確化する。

---

## 5. Codex投入ゲート

Codexへ作業を渡す前に、ChatGPTは以下を確認する。

| 確認項目 | 必須内容 |
|---|---|
| モデル設定 | モデル、インテリジェンス / reasoning effort、速度を明記する |
| ブランチ方針 | 最新 `main` から新規クリーンブランチを作る。旧ブランチ継続利用可否を明記する |
| 対象ファイル | 主対象、確認対象、変更禁止対象を分ける |
| 要求仕様 | 正確に追加、削除、変更すべき仕様を列挙する |
| 安全制約 | 仕様、文言、テスト期待値を弱めない必須文言を含める |
| テスト | 実行するローカルテストと、CI確認方針を明記する |
| Git公開Step | `git add`、`git commit`、`git push`、PR作成を明記する |
| 完了条件 | commit、remote push、PR作成、テスト、未反映事項を必須にする |
| 結果報告 | 統一ステータス、PR番号、commit SHA、CI状態、未反映事項を含める |

Codexへmerge、課題管理整理、merge後ブランチ削除を混ぜてはならない。

---

## 6. PR未作成時の追補優先ルール

Codexが仕様反映とテスト実行を完了しても、commit、remote push、PR作成が未完了の場合、その作業は完了扱いしない。

ChatGPTは、ユーザー手作業へ直行せず、原則として以下の順に対応する。

1. Codexへcommit、push、PR作成の追補指示を出す。
2. Codexが安全チェック、権限、remote、CLI、認証、GitHub連携制約で失敗した場合、ChatExec方式またはChatExec2方式へ切り替える。
3. ChatExec方式でも不適切または失敗した場合、ユーザー手作業へ切り替える。
4. いずれの場合も要求仕様、ユーザー指定文言、テスト期待値を弱めない。

同一目的でCodex追補が2回失敗した場合は、ChatExec方式またはユーザー手作業へ切り替える。

---

## 7. 統一完了状態定義

| 状態 | 定義 | 完了扱い |
|---|---|---:|
| `LOCAL_SUCCESS` | ローカル差分作成とローカルテストPASS。ただし未commit、未push、またはPR未作成 | いいえ |
| `COMMITTED` | commit済み。ただしremote未push | いいえ |
| `PUSHED` | remote branchあり。ただしPR未作成 | いいえ |
| `PR_READY` | PR作成済み。CI未確認または進行中 | いいえ |
| `CI_GREEN` | CI success。レビュー・merge判断待ち | いいえ |
| `DONE` | main merge済み。必要な課題管理整理、ブランチ整理、prune確認まで完了 | はい |
| `PARTIAL` | 一部反映、未反映事項あり | いいえ |
| `BLOCKED` | 安全チェック、権限、CLI、認証、CI等で停止 | いいえ |

Codexや外部AIが `STATUS: SUCCESS` と報告しても、PR未作成、CI未確認、main未反映がある場合、ChatGPT側では上表に従って再分類する。

---

## 8. ChatExec / ChatExec2切替ゲート

ChatExec方式またはChatExec2方式は、以下の場合に使用する。

- ChatGPT(リポジトリ編集)の直接反映が安全チェックまたはツール制約で不安定な場合。
- Codexがcommit、push、PR作成で停止し、同一目的の追補でも解決しない場合。
- ユーザーPC上のローカル差分、テスト結果、CLI実行結果を安全に確認する必要がある場合。
- 並行作業やPR/Issueコメント方式が有効な場合はChatExec2方式を優先する。

ChatExec系でも、長い実行コマンドをユーザーに繰り返し貼らせる運用は避け、配布スクリプトと結果集約を基本とする。

---

## 9. PR / CI / mergeゲート

PR作成後、ChatGPTは以下を確認する。

1. PR base が `main` であること。
2. PR head が作業ブランチであること。
3. 変更ファイルがスコープ内であること。
4. 要求仕様が弱められていないこと。
5. テスト期待値が実装不足を隠す形に弱められていないこと。
6. CIが success であること。
7. 未反映事項がない、または明示されていること。
8. merge判断がユーザー(人)の責務として残っていること。

merge後は、必要に応じて課題管理整理、リモート作業ブランチ削除、ローカル `git fetch origin --prune`、`git branch -r` 確認を行う。

---

## 10. Codex結果報告フォーマット

Codex結果報告には以下を含める。

```text
JOB_ID:
STATUS: LOCAL_SUCCESS | COMMITTED | PUSHED | PR_READY | CI_GREEN | DONE | FAIL | PARTIAL | BLOCKED
Repository:
Branch:
Commit:
Remote Push: DONE | NOT_DONE | BLOCKED
PR: #number | NOT_CREATED | BLOCKED
Local Test:
CI:
Changed Files:
Requirement Mapping:
Unreflected Items:
Blocking Point:
Next Required Action:
```

`PR: NOT_CREATED` または `Remote Push: NOT_DONE` の場合、`STATUS: DONE` または `STATUS: SUCCESS` として扱わない。
