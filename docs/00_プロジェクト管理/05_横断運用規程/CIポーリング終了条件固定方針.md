# CIポーリング終了条件固定方針

## 1. 目的

本書は、Q-Scout for SpringのPR作成後のCI確認において、`queued`、`in_progress`、一部Job完了などを完了状態と誤認しないための終了条件を定める。

Q-Scoutでは、docs更新、診断・改善ロジック修正、Codex投入、ChatExec2実行を伴うPRが発生する。CI待ちフェーズで不用意に会話を区切ると、本来継続すべきポーリングや失敗時対応が抜け落ちるため、終了条件を固定する。

## 2. 基本方針

1. `queued` は終了条件ではない。
2. `in_progress` は終了条件ではない。
3. 一部Jobのみsuccessは終了条件ではない。
4. すべての必須Jobが `completed / success` になった場合のみ `CI_GREEN` とする。
5. いずれかの必須Jobが `completed / failure`、`cancelled`、`timed_out`、`action_required` になった場合は、CI失敗または停止として扱う。
6. CI失敗時は、ログ確認、原因切り分け、修正方針提示、修正PR更新へ進む。

## 3. 終了状態定義

| 状態 | 判定 | 次工程 |
|---|---|---|
| `queued` | 未完了 | ポーリング継続 |
| `in_progress` | 未完了 | ポーリング継続 |
| 一部Job success | 未完了 | 残Jobの完了まで継続 |
| 全必須Job success | `CI_GREEN` | merge可否確認へ進む |
| 任意Job failure | `CI_FAILED` | ログ確認・修正判断へ進む |
| cancelled / timed_out | `CI_STOPPED` | 再実行または原因確認へ進む |
| action_required | `CI_BLOCKED` | 権限・承認・外部条件を確認する |

## 4. ポーリング継続原則

ChatGPTがCIを確認している場合、短時間ポーリングで完了が見込める限り、終了条件に到達するまで確認を継続する。

特に、以下の表現で処理を止めてはならない。

- 「CIが長引いているため、ここで一旦区切ります」
- 「後でCI結果を確認してください」
- 「次回、CI結果確認から再開します」

ただし、ツール制約、極端な長時間化、ユーザーからの停止指示、外部認証切れなどにより継続できない場合は、以下を明示して一旦報告する。

1. 最後に確認したrun IDまたはPR番号。
2. 現在のJob状態。
3. 未完了Job。
4. 再開時に最初に確認すべき対象。
5. 自動継続できなかった理由。

## 5. ユーザー途中入力の扱い

短時間ポーリング中にユーザーが追加指示、補足、停止、方針変更を行った場合は、ユーザー入力を優先する。

ただし、単なる待機中の確認であり、ユーザーから停止や方針変更がない場合は、終了条件までポーリングを継続する。

## 6. merge判断との関係

CIが `CI_GREEN` になっても、それだけで作業完了ではない。

PRがmerge対象である場合、以下を確認する。

1. PRがdraftではない。
2. PRがmergeableである。
3. 差分が作業スコープ内である。
4. 要求仕様やテスト期待値が弱められていない。
5. ユーザー合意済みまたは既存運用上ChatGPTがmerge可能な範囲である。

merge後は、作業ブランチ削除、local prune、local main syncへ進む。

## 7. 完了条件

CI確認を完了扱いにするには、以下のいずれかを満たす。

1. 全必須Jobが `completed / success` になり、`CI_GREEN` として次工程へ進んだ。
2. いずれかのJobが失敗または停止し、ログ確認または修正対応へ進んだ。
3. ツール制約やユーザー指示により継続不能であり、未完了状態と再開対象を明示した。

単に時間が経過した、または一部Jobがsuccessになっただけでは、CI確認完了とは扱わない。
