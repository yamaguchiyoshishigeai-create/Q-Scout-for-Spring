# Codex投入前ハンドオフゲート方針

## 1. 目的

本方針は、Codexへ実装指示を渡す前に、ChatGPT側で実施すべき検討・分担・前処理が抜けることを防ぐための横断運用規程である。

Codexは実装、複数ファイル修正、テスト更新、ビルド確認に強い。一方で、課題整理、実装境界定義、作業分担判断、最小実装指示書作成、PR確認、merge判断、課題管理整理などは、ChatGPT側で先に扱うべき場合がある。

## 2. 基本原則

Codexへ作業を渡す前に、ChatGPTは必ず以下を確認する。

1. ChatGPT(会話内)で完結できる整理作業が残っていないか。
2. ChatGPT(リポジトリ編集)で先に実施できる文書・課題管理・ブランチ作成が残っていないか。
3. Codexへ渡す範囲が、実装本体・複数ファイル修正・テスト更新などに限定されているか。
4. Codexへ渡さない範囲が明確か。
5. ユーザー(人)が実行すべき操作が混在していないか。

## 3. Codex投入前の確認項目

Codex投入用プロンプトまたは指示書を提示する前に、以下の観点を短く確認する。

| 確認項目 | 内容 |
|---|---|
| 作業分解確認 | ChatGPT(会話内)、ChatGPT(リポジトリ編集)、Codex、ユーザー(人)のどこで処理すべきかを分ける。 |
| ChatGPT側で先にできる作業 | 個票登録、課題一覧更新、既存設計確認、最小実装指示書作成、実装ブランチ作成などを先に済ませる。 |
| Codexへ渡す最小範囲 | 実装、複数ファイル修正、テスト更新、ビルド確認などCodexに任せる理由を明示する。 |
| Codexに渡さない範囲 | PR確認、CI確認、merge、課題管理整理、merge後ブランチ削除などをCodex指示へ混ぜない。 |
| 出力直前チェック | Codexプロンプトが実装本体に集中しており、不要な運用作業を含んでいないか確認する。 |

## 4. 推奨される切り分け

| 作業 | 原則の実行主体 | 理由 |
|---|---|---|
| 課題の整理・優先順位判断 | ChatGPT(会話内) | 会話文脈とユーザー意図の整理が中心であるため。 |
| 個票登録・課題一覧更新・運用規程更新 | ChatGPT(リポジトリ編集) | 文書差分が中心で、GitHub連携で安全に実施できるため。 |
| 実装ブランチ作成 | ChatGPT(リポジトリ編集) | GitHub連携で実行可能であり、作業起点を明確化できるため。 |
| 実装本体・複数ファイル修正・テスト更新 | Codex | コード変更とテスト実行を横断するため。 |
| PR本文・PRコメント作成 | CodexまたはChatGPT | 実装結果とテスト結果を持つ主体が作成する。必要に応じてChatGPTが確認・補正する。 |
| PR確認・CI確認・merge判断 | ChatGPT(リポジトリ編集) | GitHub連携で確認・merge可能であり、順次タスクmergeゲートと整合するため。 |
| merge後ブランチ削除 | ユーザー(人) | GitHub連携側で直接削除できない場合があるため。 |

## 5. Codex投入前に明示する文言

Codex投入用ファイルまたはプロンプトをユーザーへ提示する前に、ChatGPTは原則として以下の趣旨を明示する。

> ChatGPT側で先に処理できる範囲とCodexへ渡す範囲を切り分けた結果、実装本体のみCodexへ渡します。

必要に応じて、以下も併記する。

- ChatGPT側で完了済みの作業。
- Codexへ渡す作業。
- Codexへ渡さない作業。
- Codex完了後にChatGPT側で行う確認作業。
- ユーザー操作が必要になるタイミング。

## 6. Codex投入指示書のGit公開Step必須化

Codexへ実装本体、複数ファイル修正、テスト更新、ビルド確認を依頼する場合、指示書には原則として以下を明記する。

1. 最新 `main` から新規クリーンブランチを作成すること。
2. 指定対象ファイルのみをstageすること。
3. commitを作成すること。
4. 作業ブランチをremoteへpushすること。
5. GitHub PRを作成すること。
6. PR番号、commit SHA、変更ファイル、テスト結果、CI状態、未反映事項を報告すること。

ただし、Codexへmerge、課題管理整理、merge後ブランチ削除を依頼してはならない。

Commit未作成、remote push未実施、PR未作成のいずれかが残る場合、Codex結果は `SUCCESS` ではなく、`LOCAL_SUCCESS`、`COMMITTED`、`PUSHED`、または `PARTIAL` として扱う。

Codex指示書を作成する場合は、原則として `Codex指示書テンプレート.md` の項目を確認し、モデル設定、最重要制約、対象ファイル、テスト、Git公開Step、結果報告フォーマットを含める。

## 7. 禁止事項

以下を禁止する。

- ChatGPT側で先にできる個票登録、課題一覧更新、実装境界定義を省略して、いきなりCodexへ丸投げすること。
- Codexへ実装本体以外のmerge、課題管理整理、ブランチ削除などを過剰に混ぜること。
- Codex投入前に、なぜCodexが主担当なのかを説明しないこと。
- ChatGPT(リポジトリ編集)で安全に実施できる準備作業を、理由なくCodexへ渡すこと。
- ユーザー操作が必要な工程をCodex指示書内に曖昧に混在させること。
- Commit未作成、remote push未実施、PR未作成の状態を完了扱いすること。

## 8. 例外

短い単一ファイル修正、文言修正、README追記、局所的なdocs修正など、ChatGPT(リポジトリ編集)で安全に完了できる作業はCodexへ渡さない。

一方、Controller、Service、テンプレート、テストなどを横断する修正、またはビルド・テスト実行を伴う修正はCodex優先とする。

ただし、ChatGPT(リポジトリ編集)の直接操作が安全チェックまたはツール制約でブロックされ、仕様を弱めないと通らない可能性がある場合は、`安全チェック発生時の仕様不変切替方針.md` を優先し、Codex、ChatExec方式、またはユーザー手作業へ切り替える。
