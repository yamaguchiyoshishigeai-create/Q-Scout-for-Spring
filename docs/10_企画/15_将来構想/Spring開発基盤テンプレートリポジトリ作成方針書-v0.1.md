> 本書は、Q-Scout-for-Spring の現行 Web MVP / CLI / 診断ルールに対する直接要件ではなく、
> TPL-001「Spring開発基盤テンプレート抽出設計書 v0.1」を受けて、
> 今後の Spring 系ツール開発へ横展開するテンプレートリポジトリの作成方針を定義する将来構想文書である。

> 本書の内容は、現行 Q-Scout のリリース必須条件ではなく、
> 将来の `Spring-Tool-Development-Template` 作成に向けた方針として扱う。

## 1. 文書概要

### 1.1 文書目的

本書は、`Q-Scout-for-Spring` の開発過程で整備された docs 構成、改善タスク管理、AIリポジトリ作業証跡管理、Codex連携運用、開始時プロンプト方式をもとに、今後の Spring Framework / Spring Boot ベースの新規ツール開発へ再利用可能なテンプレートリポジトリを作成するための方針を定義する。

本書は、先行文書である `Spring開発基盤テンプレート抽出設計書 v0.1` を受けて、次の事項を具体化する。

- テンプレートリポジトリの目的
- 想定リポジトリ名
- 初期構成
- 最小セットとフルセットの切り分け
- Q-Scout-for-Spring から流用する要素
- Q-Scout 固有要素として除外する要素
- 初期生成対象ファイル
- Codex に渡すべき作業範囲
- ChatGPT 側で先行すべき作業範囲
- 初回適用候補
- 作成後の検証観点

本書はテンプレートリポジトリ実体の作成指示書ではなく、実体作成前の方針書である。

## 2. 前提

### 2.1 先行文書

本書は、以下の文書を前提とする。

- `docs/10_企画/15_将来構想/Spring開発基盤テンプレート抽出設計書-v0.1.md`

同文書では、Q-Scout-for-Spring の開発過程で整備された開発運用基盤を、Spring 系ツール開発全般へ横展開する方針が定義されている。

### 2.2 Q-Scout-for-Spring の位置づけ

Q-Scout-for-Spring は、Spring Framework / Spring Boot ベースの開発支援ツール群のうち、最初に実装された「Springコード品質スコアリングAI」である。

今後、以下のような関連ツールを順次開発する可能性がある。

- Spring API自動設計コンパイラ
- Springマイクロサービス依存可視化ツール
- Springセキュリティポリシーテスター
- Spring設定ミス検出CLI
- Springテスト自動生成エンジン
- Springレガシーコード自動リファクタリングツール

このため、Q-Scout-for-Spring は単体プロダクトであると同時に、今後の Spring 開発支援プラットフォーム構想の先行実装例として扱う。

### 2.3 本テンプレートの性質

本テンプレートは、Spring Boot アプリケーションのコード雛形を直接生成するためのものではない。

主目的は、以下のような **開発運用基盤** を新規リポジトリ立ち上げ時から利用可能にすることである。

- docs 階層
- 企画書テンプレート
- 要件定義テンプレート
- 基本設計テンプレート
- 詳細設計入口
- 改善タスク管理
- AI作業証跡管理
- Codex連携ルール
- PR運用ルール
- 開始時プロンプト

実装コード雛形は、必要に応じて後続フェーズで追加する。

## 3. 基本方針

### 提案名

Spring-Tool-Development-Template 作成方針

### 優先度

高

### 基本方針

テンプレートリポジトリは、Q-Scout-for-Spring から以下を抽出して作成する。

1. docs 構成

6. Q-Scout 固有の Java 実装コード

テンプレートは、最初から過度な自動化を目指さず、まずは人間とAIが共同開発を開始しやすい文書基盤として作成する。

## 4. 想定リポジトリ名

### 4.1 推奨リポジトリ名

    Spring-Tool-Development-Template

### 4.2 理由

- Spring 系ツール開発全般に使えることが分かりやすい
- 特定プロダクト名に依存しない
- Q-Scout からの派生であることを前面に出しすぎない
- 開発運用基盤テンプレートであることを表現できる
- 将来 `Config Doctor` や `Security Policy Tester` にも適用しやすい

### 4.3 代替候補

    Spring-Dev-Tool-Template

    Spring-AI-Development-Template

    Spring-Product-Starter-Template

    Spring-Tool-Project-Template

### 4.4 現時点の推奨

現時点では `Spring-Tool-Development-Template` を第一候補とする。

理由は、実装コード雛形ではなく、開発運用基盤まで含むテンプレートであることを最も自然に表現できるためである。

## 5. 公開範囲方針

### 5.1 初期方針

テンプレートリポジトリは、初期段階では **Public** で管理可能とする。

### 5.2 Public 管理が可能な理由

本テンプレートは、特定顧客情報、秘密情報、商用ロジック、非公開アルゴリズムを含まない。

主な内容は以下である。

- docs構成
- 文書テンプレート
- AI作業ルール
- 改善タスク管理方式
- 開始時プロンプトのひな形
- PR証跡テンプレート

これらはポートフォリオ性があり、公開しても不利益が小さい。

### 5.3 Private 管理を検討すべき条件

以下のいずれかを含める場合は、Private 管理を検討する。

- 商用 Pro 版専用の開発工程
- 非公開の販売戦略
- 顧客導入手順
- 独自の営業資料
- 有償サービス運用ノウハウ
- 非公開のAI活用プロンプト
- 特定企業向けの評価基準

### 5.4 結論

初期テンプレートは Public 管理を前提としてよい。

ただし、将来的に商用開発基盤まで含める場合は、Public Free 版テンプレートと Private Pro 版テンプレートを分ける。

## 9. Q-Scout-for-Spring から流用する要素

### 9.1 流用対象

Q-Scout-for-Spring から流用する要素は以下とする。

- docs 階層思想
- docs/README.md の構成思想
- 改善タスク管理方式
- TSK採番方式
- 解決済み化フロー
- AI_REPO_RESULT ブロック
- ChatGPT / Codex / ユーザー 作業主体分類
- Codex連携運用ルール
- PRブランチ検証先行ルール
- 開始時プロンプト方式
- Public Free / Private Pro 分離方針の骨子

### 9.2 流用時の加工方針

Q-Scout-for-Spring の文書をそのままコピーせず、以下の加工を行う。

- `Q-Scout-for-Spring` を `{{PROJECT_NAME}}` へ置換
- `Q-Scout` を `{{PRODUCT_NAME}}` へ置換
- 診断ルール固有の説明を削除
- スコアリング固有の説明を削除
- `qscout-report.md` など成果物名を変数化
- Springコード品質スコアリングAIという製品カテゴリを変数化
- Web MVP固有の制約をテンプレート説明へ一般化
- Render / Docker 前提は「必要時に採用する例」として扱う

### 9.3 流用しないもの

以下はテンプレート本体へ流用しない。

- Java実装コード
- Thymeleafテンプレート
- Q-Scout専用CSS / JS
- 6ルール実装
- RuleExplanation 系文書
- サンプル評価スクリプト
- Q-Scout固有のREADME本文
- Q-Scout固有のテストコード

## 13. 改善タスク管理の初期状態

### 13.1 初期TSK

テンプレートリポジトリには、初期タスクとして `TSK-001.md` を配置する。

内容は以下とする。

    管理ID: TSK-001
    件名: 初期READMEとdocs入口文書の整合を確認する
    状態: 未解決
    主担当候補: ChatGPT(会話内) / ChatGPT(リポジトリ編集)
    目的: 新規プロジェクト開始時に README、docs/README.md、PROJECT_START_PROMPT_TEMPLATE.md の整合を確認する

### 13.2 初期一覧

`改善タスク課題一覧.md` には、以下を初期表示する。

    最大TSK番号: TSK-001
    保留: 0
    未解決: 1
    確認待ち: 0
    解決中: 0
    解決済み: 0

### 13.3 解決済みフォルダ

`解決済み/` は初期状態で空でもよいが、フォルダ維持のため短い README または `.gitkeep` の扱いを検討する。

docs配下の方針としては、空ファイルよりも説明文書を優先するため、以下を推奨する。

    docs/00_プロジェクト管理/02_改善タスク管理/解決済み/README.md

## 17. Codex向け作業化方針

テンプレートリポジトリ実体の生成は、多数ファイル作成と一括置換を伴うため、Codex担当が適している。

ただし、Codexへ渡す前に ChatGPT(会話内) で以下を確定する。

1. リポジトリ名
2. Public / Private
3. 最小セットのみかフルセットか
4. scripts を初回から含めるか
5. Q-Scout由来文書をどの範囲まで流用するか
6. PRテンプレートを含めるか
7. GitHub Actions を初回から含めるか

Codex向け指示書には、以下を必ず明記する。

- 実施対象
- 実施しないこと
- Q-Scout固有語を残さないこと
- 置換変数一覧
- 最終ファイル一覧
- 検証手順
- 出力形式
- Git操作は専用手順に従うこと

## 18. 初回テンプレート作成時の非対象

以下は初回テンプレートリポジトリ作成では対象外とする。

1. Java / Spring Boot 実装コード雛形
2. Maven / Gradle の固定構成
3. Dockerfile
4. Render設定
5. Web UIテンプレート
6. サンプルプロジェクト評価スクリプト
7. Q-Scoutの診断ルール
8. Q-Scoutのレポート生成仕様
9. Figma運用の詳細手順
10. GitHub Actions の本格CI

理由は、初期段階では「文書基盤・運用基盤」のテンプレート化を優先し、実装方式に依存する部分は後続で扱う方が安全なためである。

## 19. 初回適用候補

### 19.1 第1候補

Spring設定ミス検出CLI（Config Doctor）

理由：

- CLI中心で開始できる
- 対象が `application.yml` / `application.properties` で明確
- Q-Scoutと同じく診断・レポート型にできる
- MVPが比較的小さい
- Web化前でも価値が成立する

### 19.2 第2候補

Springセキュリティポリシーテスター

理由：

- ルール診断型であり、Q-Scoutの運用基盤と相性がよい
- Public Free / Private Pro の分離がしやすい
- 診断結果レポート方式と相性がよい

### 19.3 第3候補

Springテスト自動生成エンジン

理由：

- AI活用との親和性が高い
- テスト方針、生成責務、対象範囲の文書管理が重要
- Codex連携基盤の価値が出やすい

### 19.4 結論

テンプレートの初回試験適用先は、`Spring設定ミス検出CLI（Config Doctor）` を第一候補とする。

## 20. 作成後の検証観点

テンプレートリポジトリ作成後は、以下を確認する。

### 20.1 構成確認

- 想定フォルダが作成されているか
- 空フォルダ問題がないか
- プレースホルダ文書が適切に配置されているか
- docs/README.md から主要文書へ辿れるか

### 20.2 固有語確認

以下が不要に残っていないか確認する。

- Q-Scout
- qscout
- Springコード品質スコアリングAI
- 6ルール
- qscout-report.md
- qscout-ai-input.md
- ControllerToRepositoryDirectAccessRule

ただし、由来説明や参考例として残す場合は、その旨を明記する。

### 20.3 テンプレート変数確認

- `{{PROJECT_NAME}}`
- `{{PRODUCT_NAME}}`
- `{{REPOSITORY_FULL_NAME}}`
- `{{PRODUCT_CATEGORY}}`
- `{{TARGET_FRAMEWORK}}`

などの変数が一貫しているか確認する。

### 20.4 docs導線確認

- `README.md`
- `PROJECT_START_PROMPT_TEMPLATE.md`
- `docs/README.md`
- `20_要件定義ガイド.md`
- `基本設計.md`
- `改善タスク課題一覧.md`

が相互に矛盾していないか確認する。

### 20.5 AI運用ルール確認

- ChatGPT / Codex / ユーザー の作業主体分類が残っているか
- AI_REPO_RESULT ブロックが利用可能か
- Codex連携運用ルールがプロダクト非依存になっているか
- PRテンプレートが証跡管理に対応しているか

## 22. 初期リスクと対策

### 22.1 テンプレートが重くなりすぎるリスク

対策：

- READMEで最小セットとフルセットを明確に分ける
- 小規模CLIでは 40 / 50 / 60 / 70 は後続使用でよいと明記する
- 初期利用者が全ファイルを埋める必要はないと説明する

### 22.2 Q-Scout固有語が残るリスク

対策：

- 残存語チェックを実施する
- 残す場合は「派生元例」と明記する
- 成果物名、ルール名、スコア名は変数化する

### 22.3 実装コード雛形と誤解されるリスク

対策：

- README冒頭で「開発運用基盤テンプレート」であると明記する
- Spring Bootアプリ雛形ではないと明記する
- 実装コード雛形は後続フェーズとする

### 22.4 Codex生成時に範囲が膨らむリスク

対策：

- Codex指示書で実施対象と非対象を明記する
- 初回は docs / scripts / .github に限定する
- Javaコード、Docker、CIは対象外とする

## 24. 最終結論

`Spring-Tool-Development-Template` は、Q-Scout-for-Spring の開発過程で整備された文書体系・改善タスク管理・AI協働開発ルールを、今後の Spring 系ツール開発へ横展開するためのテンプレートリポジトリとして作成する価値が高い。

初期段階では、実装コード雛形ではなく、開発運用基盤テンプレートとして作成する。

構成はフルセットで作成しつつ、利用時には最小セットから開始できるようにする。

テンプレートリポジトリの実体生成は、多数ファイル作成と汎用化置換を伴うため、Codexに渡すのが適切である。ただし、Codex実行前に、ChatGPT(会話内)で TPL-003 として生成指示書を作成し、実施範囲、非対象、変数化方針、検証観点を固定する。

以上を、TPL-002 Spring開発基盤テンプレートリポジトリ作成方針 v0.1 とする。
